# 추정 용량과 실제 저장 용량

OPT-015의 계약과 검증 기록이다. 합성 입력만 사용하며 실제 사용자 문서를 읽거나 업로드하지 않는다. 원본 입력은 수정하지 않는다.

## 보고서와 타입

- `analyzeHwpxBuffer`는 `AnalysisReport`를 반환한다. `kind: "analysis"`, `estimatedSize`, `estimatedSavingBytes`, `estimatedSavingPercent`, 선택적인 `estimatedTargetStatus`를 기록한다. `optimizedSize`, `savedBytes`, `savedPercent`, `targetStatus`는 기록하지 않으며 타입에서도 금지한다.
- 세 최적화 API, CLI 모드 실행기, 데스크톱 서비스와 preload는 `CompletedOptimizationReport`를 전달한다. `kind: "optimization"`과 실제 반환/저장 바이트의 `optimizedSize`·절감량·`targetStatus`를 사용하며 추정 크기 필드는 포함하지 않는다.
- 기존 소비자용 `OptimizationReport`는 이전 보고서를 읽기 위한 넓은 형태를 유지한다. `kind`가 없는 옛 `optimizedSize`의 의미를 소급해 판정할 수 없다. 새 분석 JSON의 소비자는 `estimatedSize`로 이전해야 한다. 추정값을 옛 실제 필드에 복제하는 호환 별칭은 만들지 않는다.
- 이미지 opportunity의 `confidence: "exact"`는 후보 리소스 인코딩 크기 측정을 뜻한다. 최종 ZIP 실측을 뜻하지 않는다. `compressedAfterSize`도 후보의 DEFLATE 9 측정값이다.

## ZIP 기반 추정

리더가 검증한 중앙 디렉터리의 파일별 압축 크기와 원본 ZIP 전체 바이트를 기록한다. ZIP 내부의 큰 BMP·XML이 이미 잘 압축된 경우 원시 바이트 절감량을 ZIP에서 빼지 않는다. 변경 없는 파일은 원본의 압축 크기를 유지한다. 후보에 대해서만 압축 바이트 차이를 적용하고, 같은 리소스의 대안은 하나만 고른다.

상세 분석은 이미지 후보를 인코딩한 다음 DEFLATE 9 크기를 측정한다. XML/메타데이터 정리는 후보 바이트를 DEFLATE로 측정한다. 빠른 분석은 이미지 후보 인코딩·픽셀 디코딩을 하지 않으며 후보 이미지 크기와 ZIP 근사치를 사용한다. 원본 헤더/주석/디렉터리와 변경 없는 리소스는 추정 기준에 남는다. raw 이름과 Unicode extra field의 이름을 연결할 수 없으면 해당 리소스의 절감을 약속하지 않는다. 원본 ZIP 정보가 없는 직접 구성 package는 명시적으로 `entry-model` 기준이다.

safe·balanced·aggressive의 모델을 따로 전달한다. safe는 리사이즈나 팔레트 축소를 빌려 쓰지 않으며 balanced JPEG 하한 추정에 aggressive PNG 절감을 섞지 않는다. 작업 선택은 리소스별 ZIP 모델에 적용하고 JPEG 품질 변경은 JPEG 후보 부분만 조정한다. 기존 단계별 리소스 절감 후보 표의 숫자는 압축 전 리소스 바이트이며 전체 ZIP 절감량과 다를 수 있다.

최종 인코딩 품질 탐색, 합쳐지는 XML 수정, 변경 경로·manifest·헤더 크기, 품질 검증에 따른 보류, 원본 유지와 ZIP 압축 레벨 차이는 추정 오차를 만든다. 빠른 분석은 작은 출력에 비해 오차율이 클 수 있다. 추정은 제출 보장이 아니며, 상세 분석도 최종 저장을 대신하지 않는다.

## 제출 기준과 배치 배분

공통 순수 모듈 `core/planning`이 `outputBytes < targetBytes`와 비례 배분을 정의한다. 기준과 같은 바이트는 미달이다. 원본이 기준 미만이어도 결과가 커져 기준 이상이면 미달이다. CLI는 같은 함수를 직접 호출한다. 데스크톱 소스는 같은 export를 참조하며, 빌드가 그 순수 모듈의 JS를 renderer의 로컬 경로로 복사한다. 따라서 Electron의 `file://`에서는 Node나 bare import 없이 같은 구현을 실행한다.

배분은 `floor((전체 기준 - 이미 사용한 실제 바이트) × 현재 원본 크기 / 남은 원본 합계)`이며 곱셈은 BigInt로 계산한다. 최소 ceiling은 1바이트이며 예산 소진을 무제한으로 바꾸지 않는다. 남은 예산이 양수일 때 각 파일이 배분 ceiling 미만이면 남은 합계 기준도 미만이다. 이미 소진한 예산은 배분으로 통과시킬 수 없다. 아주 작은 배분에서는 0바이트 이하의 결과를 만들 수 없어 달성 불가능할 수 있다. CLI의 초기 고정 배분과 데스크톱의 순차 잔여 배분은 같은 반올림 계약을 사용하되 실행 순서에 따라 남은 예산은 달라질 수 있다. 실패·취소 파일은 원본 크기를 예산에 남기고, 완료 크기가 없는 경우 추정값으로 실측을 대체하지 않는다. 최종 실패·미완료 상태를 제출 통과로 처리하지 않는다.

## 화면과 재실행

분석 화면은 `제출 가능 예상`, `추가 압축 필요 예상`, `기준 초과 예상`을 사용한다. 완료 화면의 주요 수치와 판정은 실제 저장 파일을 따른다. 계획과 실제 차이는 결과 영역에 따로 남긴다. 일괄 표는 크기 옆에 `예상`/`실제`를 붙이며 전체 완료 시 실제 합계를 표시한다. 일부 실패·취소가 있으면 미완료 확인 상태다. `다시 최적화`는 보존해 둔 분석 보고서로 계획을 재계산하며 이전 실측값을 지운다. `처음으로`는 저장 파일과 정책을 유지하고 빈 선택 화면으로 돌아간다.

## 검증

2026-10-15 Linux/Node 24.13.0: 대상 검사 후 전체 Vitest 86개 파일·672개 테스트 통과·1개 건너뛰기, 타입 검사·빌드·실제 Electron 스모크·기존 합성 corpus 2/2 통과. 스모크는 preload/IPC/worker를 지난 보고서 phase와 실제 파일 바이트, 완료 배치의 실측 표시, 초기화·포커스·설정·저장 파일 유지를 검사한다. 네이티브 워커 4개를 띄우는 기존 CLI 통합 테스트만 시작 대기를 5초에서 15초로 조정했다. 전체 병렬 실행에서는 5초를 넘겼고 단독 실행은 통과했으며, 동작 단언은 그대로 유지했다. 스크린샷·실행 JSON·합성 문서는 `.tmp/ui-audit/size-contracts-2026-10-15/`에만 보관하며 GitHub로 전송하지 않는다.


### 합성 용량 측정

`node scripts/bench/measure-size-estimates.mjs`는 사진형 연속색 JPEG, 격자 도표 PNG/BMP, 같은 이미지의 복사본이 섞인 corpus를 메모리에서 만든다. 세 모드의 기준 정책으로 인코딩한 뒤 actual−1/actual/actual+1 기준으로 재실행한다. 9/9 조합·27/27 경계를 통과했고 원본 해시가 같았다. 누락·예외·바이트/상태 불일치는 실행 실패다. 아래 signed error는 **예상 − 실제**이며 양수는 실제보다 크게 예상했다는 뜻이다. balanced는 품질 88, aggressive는 품질 60 기준이다. ### 실제 화면 관찰

승인된 로컬 Playwright가 실제 Electron 42.11.13의 기본 800×560 화면을 조작했다. 입력 선택 대화상자만 합성 파일 경로로 대체했고 나머지는 실제 IPC·core·파일 저장이다. 각 화면의 PNG를 직접 열어 확인했다. 아래 파일은 이 실행의 로컬 캡처다.

1. **단일 분석 — 통과.** `01-single-forecast.png`: 원본 1,728B, 빠른 추정 1.7KiB와 `제출 가능 예상`이 보인다. 이전의 압축 전 이미지 절감량을 빼서 작은 숫자로 표시하는 문제가 없다. 미검사 범위와 최종 확인 안내가 보인다.
2. **단일 완료 — 통과.** `02-single-actual.png`: 실제 저장 1,051B(1.0KiB)와 `제출 가능`으로 바뀐다. 원래 계획은 결과 영역에 남는다.
3. **Enter로 처음으로 — 통과.** `03-reset.png`: 결과가 닫히고 파일 선택으로 포커스가 이동한다. 저장 파일과 정책은 남는다.
4. **일괄 분석 — 통과.** `04-batch-forecast.png`: 전체 합계 설정과 예상 합계, 파일별 `예상` 표기를 확인한다.
5. **일괄 완료 — 통과.** `05-batch-actual.png`: 실제 합계와 완료 파일의 `실제` 표기를 확인한다. 제출 기준과 실제 용량을 구분해 볼 수 있다.
6. **다시 최적화 — 통과.** `06-batch-retry-forecast.png`: 분석 보고서로 계획을 복원하며 행의 실측 표기를 예상으로 바꾼다. 원본 문서로 재실행한다.
7. **부분 실패 — 통과.** `07-partial-completion.png`: 잘못된 ZIP 한 개와 정상 문서 한 개를 선택한 뒤 정상 문서만 저장된다. 합계가 기준 미만이어도 `미완료 파일 확인 필요`이며 제출 가능을 확정하지 않는다.

이 실행에서 입력 SHA256 불변·저장 파일 유지·page error 0개를 확인했다. 화면 캡처만으로 스크린리더나 전체 접근성 준수를 판정하지 않는다. 완료 배너의 `실패 0` 때문에 경고색이 되는 기존 문제와 작은 창의 밀도/확대는 OPT-024/025에 남는다.

### Windows 재검증

커밋 `d1ca2a5`, Windows/Node 24.21.0의 [CLI ZIP 실행](https://github.com/eunsang26/hwpx-optimizer/actions/runs/38671044380)과 [데스크톱 릴리즈 실행](https://github.com/eunsang26/hwpx-optimizer/actions/runs/38671027766)이 모두 성공했다. 두 실행 모두 86개 파일·672개 테스트 통과·1개 건너뛰기, 타입 검사·빌드·배포 audit를 통과했다. CLI ZIP의 실제 optimize/verify/batch/launcher smoke, 데스크톱의 합성 corpus 2/2·새 phase/실측 계약을 포함한 Electron smoke·NSIS 빌드·실제 ASAR 내 core/io entry 검사·unpacked native 파일 검사도 통과했다.

Windows 용량 측정 역시 9/9 조합·27/27 경계를 통과했고 위 표의 원본/추정/실제 바이트와 같았다. 기존 처리/저장 간격·분석 모드·리소스 측정도 통과했다. quick/default의 이미지 1/8/24개 측정에서 raw decode와 encode 요청은 모두 0개였다. 입력과 패키지는 합성이며 산출물 업로드 단계는 모두 건너뛰었다. production+shipped Electron의 moderate+ advisory는 0개였고 전체 개발/빌드 도구 advisory 20개(high 8·moderate 11·low 1)는 남아 있다.

화면별 PNG와 캡션을 함께 보는 로컬 보고서는 같은 캡처 폴더의 `index.html`이다. 7단계·7개 이미지가 렌더되는 것을 별도 Electron 창에서도 확인했다.
