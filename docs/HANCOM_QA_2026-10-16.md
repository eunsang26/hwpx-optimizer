# 현재 한컴·큰 실제 문서 검증 — 2026-10-16

OPT-021의 실제 문서 검증 기록이다. 사용자 지정 파일 하나를 비식별 사례 A로 사용한다. 실제 파일명·입력 경로·문서 내용·원본 해시·렌더링은 저장소와 외부 업로드에서 제외한다. 원본은 읽기만 하며, 별도 Windows 검증 폴더의 동일한 복사본과 모드별 결과를 사용한다. 이 PC는 사용자가 확인한 **개인 PC**이므로 기관 PC 승인 증거로 취급하지 않는다.

## 환경과 산출물

- Windows 11 Pro, 10.0.26200/build 26200, Intel Core Ultra 5 228V/8 cores, RAM 33,840,226,304바이트.
- 한컴오피스 2024 교육기관용 설치 제품 13.0.0.304, 실제 Hwp.exe/COM 버전 13.0.0.711.
- 앱 0.1.9, 최종 런타임 `209053f`; Electron 42.11.13(내장 Node 24.19.0)/sharp 0.35.5. 로컬 Windows 검사 드라이버는 Node 24.13.0이다.
- 현재 소스로 Windows unpacked 패키지를 만들어 프로젝트 밖 Windows 폴더로 복사했다. 이 실행은 CI의 별도 NSIS 설치 파일과 동일한 artifact가 아니며, 설치/서명 승인도 아니다.
- 복사한 실행 파일 234,206,720바이트, SHA256 `0b7490762e457459b6821ab57ea1785e57061564d683b57e940a00097c002ff0`; `app.asar` 5,943,372바이트, SHA256 `9905fb7f6021bdbced159f2aa23ac373234ba96b7b3fbba727f86da62d662361`.

사례 A는 94,078,344바이트, ZIP 39개 항목/해제 크기 119,816,457바이트, XML 6개와 이미지 28개(BMP 18/JPEG 7/PNG 3)를 포함한다. 최대 이미지 5,712×4,284/24,470,208 pixel이며 5개는 24MP를 넘는다. 이 경우 앱의 보호 한도가 적용되므로 모든 이미지가 압축된다는 뜻은 아니다. 내장 글꼴 선언과 OLE control은 0개다. 이 사례로 내장 글꼴·OLE의 실제 한컴 호환성을 새로 입증하지 않는다.

## 실제 문서에서 찾은 오류와 수정

`6bb65e5`의 안전 모드가 누락 리소스 오류로 출력을 거부했다. 원본 복사본은 한컴에서 열렸고 17쪽 전체를 렌더링했다. 원본 헤더에는 `isEmbedded="0"`, `binaryItemIDRef=""`인 대체 글꼴 선언 20개가 있었다. 일반적인 필수 리소스 ID 검사로 이 빈 값을 누락으로 오판했다.

[한컴 공개 모델의 대체 글꼴 구현](https://github.com/hancom-io/hwpx-owpml-model/blob/main/OWPML/Class/Head/substFont.cpp)은 비내장 글꼴을 기본값으로 사용하고 binaryItemIDRef 문자열을 기록한다. [일반 글꼴 구현](https://github.com/hancom-io/hwpx-owpml-model/blob/main/OWPML/Class/Head/font.cpp)은 빈 참조의 기록을 생략한다. 이 구현과 실제 한컴 열기 관측에 맞춰 `8ae4ffd`는 알려진 head namespace의 font/substFont, 명시적 비내장 표시 0/false, 정확히 빈 참조에만 예외를 적용한다. XML 자체는 그대로 보존한다.

합성 회귀 15개는 prefix/default/inherited namespace와 0/false 표현을 허용하고, 내장 글꼴·그림의 빈 참조, 누락된 비어 있지 않은 ID, 외부 namespace·재정의·공백 ID를 계속 거부한다. 실제 선언된 글꼴 자원의 사용과 바이트도 유지한다. 대상 3개 파일 37개 테스트, 전체 94개 파일 788개 통과·1개 skip, 타입 검사·빌드·hygiene와 Linux Electron 27개 흐름/40개 화면 조건을 통과했다.

추가로 `8ae4ffd`의 balanced 실행은 같은 경로로 JPEG를 재인코딩하면서 원래 `image/jpg`를 `image/jpeg`로 바꿔 문서 보존 검사에 걸렸다. 실제 원본은 JPEG 선언 7개에 `image/jpg`를 사용했다. `209053f`는 변경된 출력 경로에만 manifest/direct href와 media type을 갱신하도록 보완했다. 같은 경로/형식 재인코딩은 원래 표기와 상대 href를 보존하며, verifier의 허용 범위는 넓히지 않는다. 양 모드·상대/직접 href의 합성 회귀 4개는 변경 전 실패를 확인했고 관련 4개 파일 61개 테스트가 통과했다. 최종 실제 문서 세 모드와 Windows 패키지도 아래 범위에서 통과했다. 전체 94개 파일 792개 통과·1개 skip, 타입 검사·빌드·hygiene 및 Electron 27개 흐름/40개 화면 조건을 확인했다.

Windows 개인 PC에서 발견한 800×560 요청의 801×561 CSS pixel 반올림도 `6bb65e5`에서 검사에 반영했다. 1pixel 범위만 허용하며 실제 넘침·겹침·hit test 조건은 유지한다. 이전 일반 smoke의 초기 크기 실패와 완료 marker 없는 실행은 통과로 세지 않는다.

## 한컴 보존 관측

새 COM 인스턴스의 창 handle/PID가 기존 Hwp 프로세스와 다름을 확인한다. 기존 문서를 연결하거나 종료하지 않는다. 별도 복사본/결과를 열어 페이지 수·UNICODE 텍스트를 확보하고, [한컴 오토메이션 API](https://developer.hancom.com/hwpautomation)의 CreatePageImage로 **96dpi/24bit BMP, 전체 페이지**를 만든다. 문서를 저장하지 않고 소유한 인스턴스만 종료한다.

원본 복사본은 17쪽/추출 텍스트 길이 11,308(UTF-16 코드단위)다. BMP의 비압축 24bit header·크기·stride·방향을 별도의 표준 라이브러리 검사기로 확인해 padding을 제외한 전체 pixel을 대조한다. 제품 이미지 decoder를 비교에 재사용하지 않는다. 문서 화면과 텍스트를 외부 서비스나 모델의 이미지 입력으로 보내지 않는다.

세 모드 모두 실제 Windows 앱의 파일 선택 → 분석 → 저장 위치/보존 모드 선택 → 실행 → 저장 파일 재검증 → 처음으로를 통과했다. 결과 byte 수와 저장 보고서의 실측 크기가 일치하고, 초기화 뒤 입력/결과 해시가 유지됐으며 renderer page error는 각각 0개다. 최종 UI와 보고서 모두 41,943,040바이트 목표를 `missed`/기준 미달로 표시했다. 진행 이벤트 수는 11/174/35개, 관측 최대 간격은 각각 9.55/5.03/9.56초다. 처리 시간은 클릭부터 완료 표시까지이며 문서 생성·한컴 렌더링 시간과 구분한다. 이 수치는 별도 부하 통제 벤치마크가 아니다.

저장된 실제 Windows 결과를 다시 읽어 Linux 현재 core의 original+mode+resourceMappings 비교도 세 모드 모두 통과했다. 원본과 검증용 복사본의 SHA256은 최초 값과 일치했다. 세 개의 새 앱 프로세스 뒤 다시 같은 격리 프로필을 열어 빈 화면·이전 결과/목록 없음·마지막 보존 모드 및 리포트/덮어쓰기 방지 설정 복원을 확인했다. 앱 설정 JSON에 입력 경로/파일명이 없었다. 짧은 정상 종료/재시작 확인이며 기관 PC 장시간 soak는 아니다.

같은 실제 문서의 safe 실행 중 취소를 누른 뒤 148.79ms에 취소를 확인했고, 부분 출력 파일은 없었다. 유지된 계획으로 재시도하고 같은 출력 폴더에 세 번 연속 저장했다. 세 개의 서로 다른 문서/보고서 쌍이 생성됐고, 이전 출력 해시 불변·각 출력 재검증·초기화를 확인했다. 반복 구간에서 원본의 크기·수정 시각·해시와 검증용 복사본 해시는 유지됐다. 재검증/초기화를 포함한 세 반복 관측 시간은 25.52/45.84/35.55초이며 위 클릭→완료 시간과 직접 비교하지 않는다. `repeat-and-cancel.json`에 기록했다. 마지막 반복 후 새 앱 프로세스에서도 빈 화면·마지막 safe 보존 모드·설정 복원과 앱 설정의 문서 경로 비저장을 다시 확인했다. 이 세 번의 개인 PC 반복을 기관 PC 장시간 검증으로 세지 않는다.

한컴 렌더링 비교에서 balanced/aggressive의 최소 전체 페이지 PSNR은 각각 39.16/29.59dB, 최대 평균 절대 channel 차이는 0.635/2.140(0–255 기준)이었다. 96dpi 전체 페이지의 관측치이며 국소 그림 품질·고해상도 인쇄·사람의 최종 판단을 대신하지 않는다. 문서 XML 보존/이미지 품질 검증과 구분한다. 세 출력은 동일한 UNICODE 텍스트(UTF-16 코드단위 11,308개)와 17쪽 수를 모두 유지했다.

200ms 간격으로 소유한 한컴 PID의 창을 safe 116회·balanced 50회·aggressive 65회 관측했다. 복구/손상/오류/복원/경고 제목이나 표준 대화상자는 관측하지 않았다. 순간적인 대화상자 전체를 보장하지 않는다. 관측기의 과거 상태 오인/상태 파일 공유 실패 시도는 제외하고 새 실행 완료 기록만 사용한다. 최종 safe 렌더링은 `hancom-safe-confirmed`에 있다.

로컬 증거는 검증 폴더의 `runtime-evidence.json`, 모드별 `execution.json`/압축 보고서, `hancom-*/result.json`/`comparison.json`, 텍스트와 페이지 BMP, `hancom-*-dialogs.json`에 있다. 실제 문서 자료는 공유하지 않는다. 같은 폴더의 `review.html`은 17쪽 원본/선택 모드 비교와 결과 파일 링크를 제공한다. 로컬 Electron에서 세 모드 전환과 이미지 68개의 decode를 확인하며, 문서 화면 캡처는 만들거나 외부로 보내지 않는다.

사용자 확인(2026-10-16): 위 로컬 보고서의 균형·적극 결과에서 글자·표·그림 품질에 문제가 있는지 묻고 **“확인했고 문제 없음”** 응답을 받았다. 이 사례·현재 결과의 사용자 시각 확인으로 기록하며 다른 문서/환경이나 기관 PC 승인을 의미하지 않는다.

## 남은 승인 범위

- 현재 PC는 개인 PC다. 기관 Windows 10/11에서 실제 기간·반복 횟수·취소/정상 종료/재실행·UI 응답·설정 복원·앱의 경로/이력 비저장을 별도로 검증해야 한다.
- 한컴의 자체 최근 문서 기록과 앱 소유 설정 정책은 서로 다르다. 기존 한컴 기록·사용자 설정을 정리하거나 초기화하지 않는다.
- 다른 한컴 버전·글꼴/프린터 조합, 내장 글꼴/OLE가 포함된 실제 문서, 실제 인쇄물의 사람 확인은 이 한 사례의 범위를 넘는다.

이 기록만으로 OPT-021 전체 또는 기관 배포를 완료 처리하지 않는다.

## 합성 CI의 최종 범위

`209053f`의 [PR 검사](https://github.com/eunsang26/hwpx-optimizer/actions/runs/38859308738)에서 Linux Node 22.12.0·24.21.0 및 Windows CLI Node 24.21.0이 모두 통과했다. [Windows 데스크톱 릴리즈 검사](https://github.com/eunsang26/hwpx-optimizer/actions/runs/38859318306)도 792개 테스트·타입 검사·빌드·audit·NSIS/ASAR/native/로캘 및 합성 측정을 통과했다. Linux 각각과 Windows 소스/프로젝트 밖 실제 패키지 각각에서 11+4+9+3개 Electron 흐름·40개 화면 조건이 통과했다. 패키지의 글꼴은 외부 통신과 시스템 Pretendard 없이 검사했다. 두 실행의 artifact는 0개, 업로드는 skipped다. 배포 runtime moderate 이상은 0개이며 full advisory 20개(high 8/moderate 11/low 1)는 별도로 남아 있다.

CI는 합성 입력만 사용했다. 위 개인 PC 실제 문서와 이 CI 배포물은 커밋은 같지만 artifact hash와 생성 환경이 다른 별도 증거다. 후속 문서 커밋의 CI와 이 런타임 검증도 구분한다.
