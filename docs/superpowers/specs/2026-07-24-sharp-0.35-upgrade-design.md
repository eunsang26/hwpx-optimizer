# sharp 0.35 Upgrade — Design

- Date: 2026-07-24
- Status: draft (ready for implementation planning)
- Priority: **do before Windows CI smoke** (clears audit high on runtime image stack; CI smoke should exercise the upgraded win32 natives)

## 1. Problem & Goal

Root dependency is pinned at `sharp@^0.33.5` (`package.json`). `npm audit` reports a **high** advisory for `sharp < 0.35.0` (libvips CVEs). The CLI portable gate currently uses `npm audit --audit-level=critical` specifically so this high finding does not block packaging.

**Goal:** Upgrade the shared runtime to a patched **sharp 0.35.x** (audit-clean for that advisory) across:

- workspace install (`package.json` / lockfile)
- Electron Windows packaging (`prepare-win-sharp-runtime.mjs`, asarUnpack paths)
- CLI portable assembly (`scripts/cli-portable/constants.mjs` + assemble)

without changing optimizer policy (safe/balanced/aggressive), verifier thresholds, or local-only product constraints.

## 2. Confirmed requirements

- Target floor: **sharp ≥ 0.35.0**; pin an exact patch during implementation (candidate from audit fix: **0.35.3** — re-resolve at implement time).
- Host engines remain **Node ≥ 20.20.0** / pin **20.20.2** (already satisfies sharp 0.35’s Node ≥ 20.9.0).
- Keep **win32-x64** prebuilt natives; do not introduce WASM-as-default for desktop or CLI portable.
- Electron still unpacks `@img/sharp-win32-x64` outside `app.asar`.
- CLI portable stage still ships only win32 sharp (no linux/darwin packages in the ZIP).
- `REQUIRED_WIN_SHARP_FILES` / `verify-win-native-runtime.mjs` lists must match the **actual** filenames under `@img/sharp-win32-x64@<new>/lib/` after upgrade (libvips major may rename DLLs — do not assume `libvips-42.dll` forever).
- PE import check (`peImports.mjs`) still rejects `vcruntime140*.dll` / `msvcp140.dll` on packaged win32 natives.
- Optimizer image path must keep passing existing Vitest suites and perceptual gates (PSNR/SSIM) on synthetic fixtures; real-sample smoke remains local QA.

## 3. Non-goals

- No forced jump beyond the 0.35 line unless a later patch is required for install.
- No API redesign of `packages/core` image helpers unless a removed sharp API is actually used (repo currently does not use `failOnError`, `paletteBitDepth`, `jp2k`, or deprecated `sharpen` props).
- No change to JPEG quality / resize budgets / mode policy.
- No AVIF pipeline work (optimizer does not emit AVIF for HWPX BinData today).
- No Windows CI smoke in this project (separate spec).

## 4. Approaches considered

| Approach | Description | Trade-off |
| --- | --- | --- |
| **A — Direct pin to 0.35.x (recommended)** | Bump root `sharp`, sync CLI portable `SHARP_VERSION`, sync `prepare-win-sharp-runtime.mjs`, refresh native file lists, full test + portable rebuild | One coordinated bump; clear audit story |
| B — Stay on 0.33 + ignore advisory | Keep `--audit-level=critical` workaround | Leaves known high on image stack |
| C — Jump to latest major beyond 0.35 if released mid-work | Only if 0.35 line unavailable | Extra churn; avoid unless forced |

**Recommendation: A.**

## 5. Breaking changes to account for (sharp 0.35.0)

From upstream changelog (v0.35.0):

- Drop Node 18 (OK — repo already Node 20.20.2).
- Remove automatic `install` script; prebuilts expected, source build opt-in.
- `limitInputChannels` default 5 (watch multi-channel edge inputs in tests).
- Removed deprecated constructor/metadata/sharpen APIs (no current usage found).
- `format.jp2k` → `format.jp2` (no current usage found).
- libvips upgraded (native file names / sizes may change).

## 6. Touch surfaces (inventory)

| Area | Path |
| --- | --- |
| Root dep | `package.json` `dependencies.sharp`, `package-lock.json` |
| CLI portable pin | `scripts/cli-portable/constants.mjs` (`SHARP_VERSION`, `SHARP_WIN32_PACKAGE`, `REQUIRED_WIN_SHARP_FILES`) |
| CLI portable tests | `scripts/cli-portable/constants.test.ts`, assemble/verifyStage tests |
| Electron win sharp prep | `scripts/prepare-win-sharp-runtime.mjs` (hardcoded `@img/sharp-win32-x64@0.33.5`) |
| Electron unpack verify | `scripts/verify-win-native-runtime.mjs` |
| Electron builder config | `package.json` `build.asarUnpack` / `files` exclusions (paths stay `@img/sharp-win32-x64` unless package layout changes) |
| Docs | `docs/RELEASE.md` (audit-level note), `CLAUDE.md` / packaging notes if they pin 0.33.5 |

## 7. Verification contract

1. `npm ci` / `npm install` succeeds on Linux with Node 20.20.2.
2. `npm test` — full suite green.
3. `npm run typecheck` && `npm run build`.
4. `npm audit --audit-level=high` no longer fails for the sharp advisory (other unrelated advisories may remain — document residual).
5. `npm run build:win-portable` + `npm run release:verify-cli-portable` — stage has required win32 natives, PE check passes, host JS smoke passes.
6. Optional local: `HWPX_OPT_SMOKE_INPUT=sample2.hwpx npm run release:verify-cli-portable-smoke`.
7. Optional local: Electron `release:verify-win-native` after a Windows pack.

## 8. Roll-forward audit policy

After upgrade, if `npm audit --audit-level=high` is clean (or only unrelated low/dev advisories remain), **tighten** CLI portable gate from `--audit-level=critical` toward matching `release:preflight` (`--audit-level=moderate`) **only if** that does not re-block CI. Prefer: critical → high if sharp is fixed and remaining are low-only; document any intentional exceptions.

## 9. Risks

- DLL rename breaks hardcoded file lists → caught by stage/native verifiers.
- Perceptual metrics drift on fixtures → adjust fixtures only if thresholds falsely fail; do not loosen mode thresholds without evidence.
- Electron `prepare-win-sharp-runtime` version drift vs root lockfile → single source of truth should be `SHARP_VERSION` from `cli-portable/constants.mjs` or a shared `scripts/sharpPin.mjs` (prefer shared pin module if two hardcodes already diverge).

## 10. Success criteria

- Runtime + portable + Electron prep all on the same sharp 0.35.x pin.
- Sharp GHSA for `<0.35.0` cleared.
- No product/safety rule regressions; original files never overwritten.
- Spec/plan only in this document set — implementation is a separate execution.

## 11. Open decisions (resolved for plan)

1. **Shared pin module:** Yes — introduce `scripts/sharpPin.mjs` exporting `SHARP_VERSION` used by CLI portable constants and `prepare-win-sharp-runtime.mjs` (avoid triple hardcode).
2. **Exact patch:** Prefer newest 0.35.x available at implement time that installs prebuilts for linux-x64 + win32-x64; start with 0.35.3 if still current.
